Permission Boundaries Explained: What They Cap and What They Do Not

Published 2026-11-02 by the Cloud Notes team.

A permissions boundary is a managed policy that you attach to an IAM user or role. It sets the maximum permissions that the identity-based policies of that principal can grant. A boundary never grants a permission by itself.

The effective permissions

For a request from a principal with a boundary, the effective permissions are the intersection of the identity-based policy and the boundary. An action that the identity policy allows but the boundary does not is denied.

Resource-based policies are a different case

A common belief is that a boundary also limits resource-based policies. That is only partly true. In the same account, if a resource-based policy (for example an S3 bucket policy) names the IAM user directly as the principal, the boundary does not limit that grant. The request is allowed even if the boundary does not allow the action.

If the resource-based policy names an IAM role session, the boundary does apply. If it names the role ARN itself, the boundary applies too.

Explicit deny still wins

An explicit deny in any policy, including the boundary or an SCP, overrides every allow.

Why teams use boundaries

  • Delegate role creation to developers without privilege escalation.
  • Require that every new role created by a pipeline carries the same boundary.
  • Cap blast radius for automation users.

Checklist

  1. Create one boundary policy per trust level.
  2. Add an iam:PermissionsBoundary condition to the policy that allows iam:CreateRole.
  3. Test with the IAM policy simulator, including bucket policies that name users directly.
